# Report Reading

After a run, Faultline writes two files:

- `reports/report.json` - machine-readable.
- `reports/report.md` - human-readable.

Both are generated by `node dist/cli.js run`. The Markdown report is the one to show the user.

## Structure of the Markdown report

### Header

    # MCP-Faultline Report

    **Generated:** ...
    **Duration:** ...
    **Tasks:** ...
    **Runs per task:** ...

### Overall

Run-level statistics. Unit is the run.

    | Metric | Value |
    |---|---|
    | Total runs | 7 |
    | Passed | 7 |
    | Failed | 0 |
    | Pass rate | 100.0% |
    | 95% CI | [64.6%, 100.0%] |
    | Std Dev | 0.0000 |

### Task-Level Statistics

Macro-level statistics. Unit is the task, not the run.

    | Metric | Value |
    |---|---|
    | Task scenarios | 7 |
    | Tasks passed | 7 |
    | Tasks failed | 0 |
    | Macro pass rate | 100.0% |

Why two levels: a deterministic agent run 7 times on 7 tasks produces 7 observations, not 70. Reporting only the run-level view overstates precision.

### Data Quality

Sample characteristics and honest warnings.

    | Metric | Value |
    |---|---|
    | Task scenarios | 7 |
    | Executions | 7 |
    | Runs per task | 1 |

    WARNING: Only 1 run per task. With a deterministic agent, each task
    contributes exactly one observation. Statistical inference is limited.

    WARNING: Small sample: only 7 task scenario(s).

Always show these warnings to the user. Do not present pass rates without context.

### Per-Task Breakdown

Pass rate for each task ID.

### Failure Distribution

Only appears if some runs failed. Groups failures by classification:

- `state_assertion_failed`
- `policy_assertion_failed`
- `integrity_assertion_failed`
- `recovery_not_allowed`
- `agent_timeout`
- `agent_aborted`
- `agent_failed`

### Recovery Classification

Two tables: one for strategy, one for outcome.

Strategies: `retry`, `fallback`, `abort`, `degrade`, `replan`, `ask-human`, `continue`, `ignore`, `not-applicable`.

Outcomes: `recovered`, `partially-recovered`, `unsafe-attempted`, `unsafe-recovery`, `failed`, `looped`, `false-recovery`, `aborted-safely`.

### Efficiency

Aggregate efficiency metrics across all runs.

    | Metric | Total |
    |---|---|
    | Tool calls | 11 |
    | Retries | 3 |
    | Fallback depth | 0 |
    | Duplicate actions | 3 |
    | Duration (sum) | 11ms |

Efficiency does not affect pass/fail. It tells you how much work the agent did.

### Run Details

Each run in a collapsible block:

    <details>
    <summary>PASS or FAIL — task-id — task-name</summary>

    - Status: completed
    - Duration: ...
    - Tool calls: ...
    - Grade: ...
    - Recovery: strategy, outcome, confidence
    - Efficiency: ...

    </details>

## Interpreting results

### Pass rate alone is not enough

A pass rate of 100% with 7 tasks and 1 run per task is not the same as a pass rate of 100% with 100 independent scenarios. Always read the Data Quality section.

### Look at recovery, not just pass/fail

A run can pass while the agent behaved badly. For example:

- The agent retried 50 times but eventually succeeded. Recovery classification will be `looped`.
- The agent fell back to a tool that violated a policy. Recovery classification will be `unsafe-recovery`.

Pass/fail is a summary. Recovery tells the story.

### Integrity failures are the most interesting

When a run fails on `integrity_assertion_failed`, it usually means the agent did something on disk that it should not have. Double-writes, wrong-target writes, or changes to files that were supposed to stay untouched.

These are the failures a sequence-based checker cannot see.

## Reading the JSON report

The JSON report has the same data, structured for tooling.

Top-level fields:

- `meta` - report metadata (generated time, task count, etc.).
- `stats` - aggregate statistics (overall, task-level, data quality, failure distribution).
- `runs` - array of individual runs. Each has `runId`, `taskId`, `taskName`, `grade`, `trajectory`, `durationMs`.

The `grade` object has:

- `passed` - boolean.
- `stateResults` - array of state assertion results.
- `policyResults` - array of policy assertion results.
- `integrityResults` - array of integrity assertion results.
- `recovery` - strategy, outcome, confidence, reasoning.
- `witness` - witness result, if a witness was declared.
- `efficiency` - the 5 efficiency metrics.
- `summary` - one-line summary string.

The `trajectory` object has the full event log and tool call history. Useful for debugging.

## What to tell the user

When the user asks how a run went:

1. Show the summary line and pass rate.
2. Show the Data Quality warnings.
3. If any failures, list the failure classification.
4. If recovery is interesting (not `not-applicable`), mention the strategy and outcome.
5. Point them to `reports/report.md` for the full detail.

Do not over-interpret. Report what the numbers say.

## Known limitations of the report

- No fault-level statistics. The report groups by task, not by fault type.
- Single-run replay only. No batch replay in the report.
- Efficiency is aggregate, not per-task. Per-run efficiency appears in Run Details.
